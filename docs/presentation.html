01 — El Problema

Rompecabezas físicos como grafos

Rompecabezas de madera con piezas interconectadas mediante tabs (picos) y huecos. El sistema almacena la estructura y genera instrucciones ordenadas de ensamblaje manejando piezas faltantes.

🔢

Piezas numeradas

Número físico único + etiqueta descriptiva para identificar cada pieza durante el armado.

🔌

Conectores etiquetados

Cada tab o hueco lleva una letra local (A, B, C…) marcada con cinta adhesiva, local a la pieza.

⚠️

Piezas faltantes

El sistema arma todo lo posible y reporta exactamente qué sección no puede completarse.

El problema es fundamentalmente relacional — no importa la forma ni el color de cada pieza, sino únicamente qué conector encaja con cuál. Esa observación guía la elección de tecnología.

02 — Tecnología

¿Por qué Neo4j?

En un rompecabezas, el dato central es la conexión. En Neo4j existe como arco de primer nivel; en SQL sería una fila en una tabla de unión que solo cobra sentido con un JOIN.

Traversals nativos

La pregunta «¿qué pieza se conecta a esta?» es un salto de dos arcos en Cypher. En SQL involucraría cuatro tablas y varios JOINs.

Subgrafo aislado por puzzle

Agregar un nuevo rompecabezas es insertar un subgrafo sin tocar los existentes. Sin scripts de migración.

IDs globales

Formato puzzle_id__local_id — dos puzzles distintos pueden tener P01 sin colisión en Neo4j.

3 constraints UNIQUE

Puzzle.id, Piece.id, Connector.id — creadas automáticamente al correr seed.py.

CONNECTS_WITH bidireccional

Almacenado en ambas direcciones — cualquier traversal funciona con un único patrón MATCH sin manejar dirección.

-- Inserción idempotente con MERGE (ambas direcciones)
MATCH (ca:Connector {id:$ga}), (cb:Connector {id:$gb})
MERGE (ca)-[:CONNECTS_WITH]->(cb)
MERGE (cb)-[:CONNECTS_WITH]->(ca);
04 — Algoritmo

BFS de ensamblaje  O(n + m)

BFS desde una pieza inicial elegida por el usuario. Instrucciones en orden de distancia — primero adyacentes, luego a dos pasos.

1

Cargar grafo en memoria

Una consulta Cypher materializa todos los vecinos. Sin latencia de red por iteración del BFS.

2

Expandir desde pieza inicial

Por cada conector se consulta su vecino vía CONNECTS_WITH y se encola si no fue visitado.

3

Manejar piezas faltantes

Pieza faltante → MISSING emitido, rama bloqueada sin abortar el recorrido.

4

Reportar inalcanzables

Piezas disponibles pero bloqueadas por un faltante se reportan al finalizar.

⬤ START
⬤ PLACED
⬤ MISSING
-- vecindad materializada al inicio
MATCH (:Puzzle {id:$pid})
  -[:CONTAINS]->(:Piece)
  -[:HAS_CONNECTOR]->(ca:Connector)
  -[:CONNECTS_WITH]->(cb:Connector)
WHERE ca.puzzle_id = $pid
  AND cb.puzzle_id = $pid
  AND ca.local_id < cb.local_id
RETURN ca.local_id AS a,
       cb.local_id AS b;

Cargar el grafo de una sola vez evita la latencia de red en cada iteración — más eficiente que consultar Neo4j por cada paso del BFS.

04 — Algoritmo

Manejo de piezas faltantes

La disponibilidad de cada pieza se persiste en Neo4j como propiedad available del nodo :Piece. Desde la interfaz el usuario puede marcar o restaurar piezas — el cambio se escribe inmediatamente a la base de datos.

-- marcar / restaurar desde Neo4j
MATCH (pc:Piece {id:$gid})
SET   pc.available = false;  -- faltante
SET   pc.available = true;   -- restaurar

MISSING emitido. Se registra qué conector debería unirse y de qué pieza falta.

Rama bloqueada. La pieza faltante no se encola — sin instrucciones imposibles de ejecutar.

Rutas alternativas. Piezas alcanzables por caminos que no pasan por la faltante se ensamblan normal.

Reporte final. Piezas disponibles pero inalcanzables se listan al terminar.

-- el BFS deriva M desde el grafo
M = {p ∈ P | p.available = false}

visited = {s}; queue = [s]
emitir START

mientras queue no vacío:
  u = queue.pop_left()
  para cada conector c_u de u:
    v = pieza(vecino(c_u))
    si v en M:
      emitir MISSING; continuar
    si v en visited: continuar
    visited.add(v); queue.append(v)
    emitir PLACED

para p en P - visited - M:
  emitir MISSING: inalcanzable

El estado faltante es persistente entre sesiones — no es un parámetro pasado en tiempo de ejecución, sino una propiedad del grafo en Neo4j.
